How a workout gets decided

WallCrawl has no model runtime. A pure Kotlin pipeline turns a stored profile, a bundled catalog and bounded local history into one session. Hard rules decide what is legal, comparators decide what is chosen, and a validator rejects anything that breaks the contract. The same inputs and generation index always give the same plan.

Stage 2 · ExerciseEligibilityPolicy

Legality is decided before ranking

Every exercise gets a typed decision. If nothing survives, the failure names the first stage that emptied the pool, and the planner never falls back to unreviewed work.

Stage 3 · FakeWorkoutPlanner

Selection is a sorted list

The planner picks a split from high-priority muscles it can actually fill, falling back to the default rotation. The rotation advances with the completed-workout count, or the program slot. Session length sets the slot count: up to 35 minutes gives 3 exercises, up to 55 gives 5, and longer gives 6. Up to 3 slots are compounds, and at least one slot always stays an accessory.

Compound order

  1. Trains the split as its own purpose
  2. No unresolved capability penalty
  3. Supported-regression preference
  4. No above-experience penalty
  5. Frequency and recency preference
  6. Higher legacy fatigue ordinal
  7. Stable exercise ID

Accessory order

  1. Trains the split as its own purpose
  2. Isolation before compound
  3. Has programming metadata
  4. No unresolved capability penalty
  5. Supported-regression preference
  6. No above-experience penalty
  7. Frequency and recency, fatigue, then ID

Compounds also spread across movement patterns, one per pattern first, with a fallback to repeats. isStrengthWork() returns false for all 14 catalog stretches, so they can never enter a generated session.

Stage 3 · Prescription

Dose can only shrink

DefaultExercisePrescriptionFactory builds a base prescription and applies progression or an accepted deload. StateBasedTrainingPolicy then caps it and re-checks the capability and training-constraint rules, so a gap in the gate cannot let a restriction through. It never invents a load: with no history or confirmed baseline, the load stays null.

The states production derives today, under the default V2 policy. BUILD and DEVELOP are defined at 12 weekly and 4 per exercise, but are not currently derived.

One-variable progression

Two latest comparable attempts must be fully completed, confirmed manageable and carry qualifying effort. Then exactly one axis moves: +2.5 kg, +1 rep range, −2.5 kg assistance, or +5 seconds. Weight steps convert to the user's unit. The engine also defines +25 m for distance, but distance work is not admitted to automatic planning.

Rest classes

Short, moderate and long map to 60, 90 and 180 seconds. An explicit stored user preference wins.

Stage 4 · ProgramValidator

Nothing is shown until the whole plan passes

  • Structure

    IDs exist, sit in the candidate set and match the exercise type.

  • Truthful labels

    The advertised split and each focus muscle must be trained by the session.

  • Declared constraints

    Exclusions, unique IDs, and any declared families or patterns.

  • Load provenance

    Every number traces to a held source or an authorized progression.

  • Duration agreement

    The estimate must be in bounds and within one minute of the shared estimator.

  • Weekly dose

    Completed plus proposed sets must fit the allowance, per direct primary muscle.

If the only problem is an exceeded allowance, one repair pass may reduce targetSets, keeping at least one set per exercise. A repaired exercise also reverts to its pre-progression reference and records HOLD_VALIDATION_REPAIR. Repair cannot add, drop or swap exercises. At start, TodayViewModel rebuilds the context, compares the digest and revalidates with repair off, so a stale plan is reported instead of started.

Injury seams

Where health constraints would plug in

Profile

TrainingConstraint has six joint labels plus LOW_IMPACT_ONLY. There is no condition, region, phase or end date.

Gap

A condition model needs Room schema 17, an archive format bump and a place in the context digest.

Exercise metadata

clearedTrainingConstraints is enforced in the importer, parser, gate and policy, and every record leaves it empty.

Gap

Content, not code. The contract reserves filling it for the human sign-off pass.

Session shape

A generated session has compound and accessory slots only, and stretches are excluded from both.

Gap

No warm-up, mobility or rehab block exists. Prescribed stretches need a new slot type that stays out of the strength dose ledger and focus rules.

Catalog

There are 14 stretches, and none is a piriformis or figure-four stretch. Glute work such as clamshell and glute-bridge already exists.

Gap

New entries need illustrations, Spanish overlay text and provenance. The upstream catalog is pinned, so additions need an owned source.

Feedback

PAIN_STOP is recorded per set. Like any stopped set, it holds progression and disqualifies capability evidence.

Gap

The planner does not distinguish pain from any other stop reason. Using it as a signal must stay a user-facing offer, not an inference.

Manual templates

Templates bypass the gate on purpose and warn only about equipment.

Gap

A declared condition would need its own warning here, without hiding exercises.

Recorded limits

Boundaries this feature has to change or respect

Exclude medical, injury-prevention, diagnostic, and unsupported performance claims.ROADMAP.md:758, Package 11
A clearance is a reviewer's product judgement about a self-reported label; it is not a diagnosis, and reviewer agreement is not clinical validation.docs/reviewed-capability-eligibility.md:122-124

SafetyCopyTest fails the build on injury, prevention, healing and joint-protection vocabulary in either language. The evidence review also rules out numeric joint-stress and injury-risk scores. A rehab feature is a product decision that reopens these rules, so it should be recorded in the roadmap first.
